# Formal execution changes

On 2026-11-04, control returned to the Mac agents; server pi is stopped. The existing E3 A100 and run directory are retained.

The original base-direct path completed 91 actual GSM8K rows in 798.50 seconds of recorded generation time (8.77 seconds/question). Extrapolating that initial rate to the remaining 5,909 questions gives 14.4 hours for this condition alone; this estimate does not cover other datasets or training.

The formal launcher now requests base-direct batches of 16. It preserves the model/revision, test data, prompt construction, greedy decoding, EOS, 512 new-token limit and 4,096 total-token budget. Prompts with less than 512 tokens of remaining context use the existing single-item path. Inputs use left padding with attention masks. Outputs retain the original unpadded prompt and real generated tokens through EOS; batch completion padding is excluded from trajectories and action masks.

Each resumed execution records its source commit, batch size and existing-row count in the evaluation `.executions.jsonl`; existing rows and their original metadata stay intact. New rows record the execution commit, batch size and wall time. `seconds` is amortized batch time, not single-request latency. BF16 batching may change some greedy branches through numerical rounding; no token-for-token identity or speedup is claimed without actual observations.

Tool evaluation and training remain unchanged in this first optimization. No new runtime or preliminary model run is involved. The change follows the [Transformers 4.51.3 batching guidance](https://huggingface.co/docs/transformers/v4.51.3/llm_tutorial#padding-side) and the pinned generation implementation.

The first two formal direct batches completed 32 new questions in 24.8064 seconds (0.7752 amortized seconds/question), while the 134 previously completed rows were retained. This small initial observation is roughly 11.3 times the original throughput; it is not an estimate for every dataset or training stage.

Subsequent tool-enabled evaluations now request batches of 8. Each trajectory independently stops at its EOS, closing tool-call delimiter, or remaining context budget; a stopping-criteria callback records its exact first stopping length before other rows finish. Per-item tool limits, tool execution, parsing, rewards and tool-output loss masks remain unchanged. Active trajectories are regrouped at each model turn. The base-direct process already running is left untouched. The controller writes `.runtime-revision` with the deployed tracked-source commit so later Python stages record the current code rather than inheriting the old wrapper commit. Existing rows keep their earlier provenance.

The same batched tool rollout implementation is used for the future cold-start collection (up to eight distinct training questions, at most two attempts per question, exactly 500 accepted trajectories) and for each GRPO group of eight responses to one question. Temperature remains 1.0 with no top-k/top-p truncation. Group size, sampled questions, 300 steps, old/reference probabilities, objective, optimizer and update epochs remain unchanged. Batching changes the order in which random draws are consumed; seeds 42/43/44 will all start under this recorded implementation. No existing training checkpoint is being resumed under a changed sampling implementation. SFT and GRPO gradient computation are unchanged.

The real prepared dataset was copied from attempt 01 to `gdrive:exp/datasets/e3` with rclone exit code 0. The rollout source archive `554b909.tgz` was copied to `gdrive:exp/runs/E3/source/`. These are actual transfers, not native Drive mounts. Future closed evaluation files, cold trajectories and SFT/GRPO stage logs are also copied using the existing `EXP_CHECKPOINT_REMOTE`; checkpoint copying remains ordinary `rclone copy`. Copy failure retains local files and surfaces its real nonzero status. No additional validation run or persistence state machine is introduced.

A subsequent reading of the running A100 showed 12,584/40,960 MiB used, 27,858 MiB free and 36% utilization at direct batch16. The ongoing direct process was retained. Later tool evaluations and cold collection were increased to batch32. GRPO still uses eight questions and eight samples per question: four complete groups are generated together in each 32-trajectory batch, then advantages are computed separately within each original eight-response group. There is no optimizer update between these rollout batches. This scheduling change does not increase G, Q or the number of training steps. Its actual speed and peak memory will be recorded when the formal stages are reached.

## Priority order without removing evaluations

At the user's request, the current direct evaluation is paused after saving its completed raw rows. GSM8K500 and HotpotQA500 are already represented in that file; its remaining GSM-Symbolic rows are deferred. `scripts/run_priority.sh` runs base-tools on those exact 1,000 core test rows, then each seed 42/43/44's full cold collection, SFT and 300-step GRPO before that seed's core comparisons. It then completes every original 6,000-row evaluation, including all 5,000 GSM-Symbolic rows. E2 remains a separate pending adapter comparison.

Core results live under `results/core/` with 1,000-row metadata and a separate Drive directory. Before full evaluation, the unchanged core generations are copied into the full result file with an explicit `seeded_from_core` provenance record and a 6,000-row *plan*, then only missing task IDs are generated. A 1,000-row file is never reported as a completed 6,000-row evaluation. Dataset membership, split, scoring, prompts, train sizes, seeds and training steps are unchanged; the change is execution order. No model request is repeated to improve an answer.
